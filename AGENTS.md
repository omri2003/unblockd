# unblockd: notes for agents working on this repo

Read this first. It is the whole picture: what exists, why it's built this way, and the traps
that already bit. Keep it current: **docs move with the code**, in the same commit.

## What it is

A dependency-aware ticket board for humans and AI agents. One ticket = one JSON file inside a
project repo (`<project>/tickets/`), so ticket changes are committed with the code they describe.
Front doors over one core: a web board (`unblockd.web`), an MCP server (`unblockd.mcp_server`),
a CLI (`unblockd.cli`), and a chat that asks Claude about the boards (`unblockd.chat`).

## Data model

Ticket fields (`FIELDS` in store.py; add a field there and API + MCP accept it): `title`,
`status` (todo|doing|review|done writable; `pending` is derived only: writing it is refused, a stored `pending` from an old file is read as todo), `priority` (P0-P3|null), `owner`, `pillar`, `pillar_step`,
`section`, `blocked_by` (ids), `parent` (id of the group/epic this ticket is a part of; NOT a blocker), `waiting_on`, `done_at` (read-only, UTC ISO: set by create / update / `complete()` when status becomes done, cleared when it leaves done; old tickets lack it and the UI falls back to `updated`), `asked_at` / `asked_by` (read-only: `ask()` sets both to now / the agent, `answer()` clears them; a `waiting_on` set or changed by update gets `asked_at` = now if empty and never `asked_by`, so it is a hand-parked ticket; clearing `waiting_on` clears both; writing either directly is refused like `result`), `body`, `tags` (lowercase; `agent:<name>` routes),
`done_when` (list of short acceptance criteria: the bar for done, apart from the background in `body`; shown at the top of `context()` and copied as `done_when` onto the `complete` note; the drawer lists it as a checklist and the edit form takes one per line; not copied by split),
`proposed_by` (read-only: the agent that created the ticket on a board with `agent_tickets: "propose"`; set by `create(agent=)`, cleared by `accept()`; writing it is refused like `asked_by`; while set the ticket is pending), `touches` (paths/globs the work edits), `skills` / `mcp` (names from the board's registries; validated in `Store._check_caps` like `components`: unknown name -> TicketError listing the registry, names already on the ticket tolerated, deduped; copied by split; NOT in the schema `required` list), `components` (keys of the board's architecture notes the ticket changes: the explicit link to the Map; validated in `Store._check_components` against `knowledge.components` (lazy import, knowledge imports store): unknown key -> TicketError listing the board's keys, architecture off or empty -> refused with the setup steps, keys already on the ticket are tolerated so a removed note never locks it; deduped, order kept; copied by split), `milestone` (a key of the board's `milestones`: the roadmap version the ticket ships in, separate from `parent`; validated in `Store._check_milestone` (unknown -> TicketError listing the keys, no milestones -> refused with the setup step, a key already on the ticket tolerated so a removed milestone never locks it); copied by split; list filter `milestone=` with `-` = none), `docs` (repo paths/folders/globs to read), `result` (null until `complete()`: {summary, files, refs, handoff, by, at}; see Claims), plus `id`,
`created`, `updated`, `rev` (read-only integer, bumped by `Store._write`, i.e. every write of the ticket file: create = 1, old files read as 0; writing it is refused like `result`. `claims.json` is separate, so heartbeats and `_keepalive` do NOT bump it. `update(..., expected_rev=)` raises `Conflict` (a `TicketError`, REST 409) when it differs under the lock; REST `PATCH` reads `If-Match: <rev>`; no header = last write wins; CLI/MCP send none. The UI edit form sends the rev it was opened with (`data-rev`), on 409 reloads and keeps the draft).

Derived on every read (`_decorate`): `effective_status` (todo with an open blocker, a `waiting_on` or a `proposed_by` = pending),
`open_blockers`, `blocks`, `children` + `progress` {done, total} (direct children only), `unblocks` (open tickets downstream, transitive), `missing_blockers`,
`stale_days` (doing only), `score` = PRIO_WEIGHT (P0 8, P1 4, P2 2, P3 1) x (1 + unblocks),
`agent` (routed profile), `claim` (live claim: agent, profile, claimed_at, heartbeat_at, note),
`files` (names attached in tickets/files/<ID>/).

Rules enforced in the store: IDs `PREFIX-N` (create with a prefix -> next free number, also
skipping numbers in `legacy_files`); `delete` runs under the lock: drops the claim, removes `tickets/files/<ID>/`, logs `deleted`, and returns the ticket plus `referenced_by` (tickets whose `blocked_by`/`parent` still name it; they are not edited and show it as a missing blocker); `blocked_by` loops refused with the loop spelled out; `blocked_by` ids ADDED by create/update must exist ("no ticket X on this board"), ids already on the ticket that went missing are tolerated (split children inherit them too); `parent` must exist and may not loop (create/update; `list(parent=X)`, CLI `list --parent`, MCP `list_tickets(parent=)`; no REST filter (the UI filters client-side); deleting a parent leaves children pointing at it, shown with no `children` on anyone);
a profile-named worker cannot set `doing`/`done`/`review` through `update` (see Worker guardrails under Traps);
setting `doing` on a ticket with open blockers is refused (in `update`, so web/MCP/CLI all get it; `claim` only takes ready tickets);
owners and pillars must be the configured ones; unknown `agent:<x>` tags refused.

## Config: `<tickets>/unblockd.json`

Optional; `DEFAULT_CONFIG` in store.py is the schema and unknown keys are refused. Keys:
`id`, `title`, `owners` [{name, kind: human|agent}], `default_owner`, `pillar_label`, `pillars`
[{key, name, color, color_dark}], `stale_days`, `wip_limit` (int or null: the UI's In-progress WIP badge; none when null), `done_window_days` (int > 0, default 7: the board's Done column shows only tickets done that recently, UI only; edited in this file, there is no settings form), `lease_minutes`, `legacy_files`, `agents`
[{name, tags, pillars, model, instructions, docs}; other keys refused, owner `kind` must be human|agent], `docs` (knowledge for every ticket),
`skills` {name: {path, description?}} and `mcp` {name: {hint, doc?, required?}} (registries of what the agent harness provides; unblockd declares, never starts a server or stores a secret; validated in `store._check_caps` at load: names `NAME_RE`, skill `path` and mcp `doc` = an existing text file inside the project (`knowledge._inside`) and NOT under the tickets folder, description one line <= 200, hint required one line <= 300, unknown keys refused so no command/url/env), `use_skills` / `use_mcp` (registry names every ticket gets; the simplest board level that still lets a ticket add one that is not board-wide: "every registry entry" would leave nothing for a ticket to add), `agents[].skills` / `mcp` (registry names; unknown ones refused), `context_budget` (chars inlined per context, default 60000), `architecture` (repo folder of component notes, default `docs/arch`; on when the folder exists, `null` = off), `review` (bool, default false: the review gate, see Claims), `schema` (null = off; else `{prefixes: {PREFIX: meaning <= 80 chars}, required: [done_when|priority|touches|docs|pillar|owner|parent|body], tags: [...], body_template}`, every sub-key optional, unknown ones refused; see Schema and proposal gate), `agent_tickets` (`open` default | `propose`: the opt-in proposal gate), `session_tickets` (int > 0 or null, default 5) and `docs_resend` ({claims, minutes} ints >= 0) (see Worker guards), `worker_tools` / `agents[].tools` / `agents[].tools_off` (MCP tool names, `TOOL_RE`; edited from the Agents panel), `milestones` (the roadmap, `[{key, title, goal?, exit_criteria?, target?, closed?}]` in order; validated in `_check_milestones`: key `MILESTONE_RE`, unique, title <= 80, goal one line <= 300, exit_criteria <= 20 lines, target an ISO date, closed bool, unknown keys refused).

## How the pieces work

- **Boards**: `UNBLOCKD_ROOT` (folders of projects) is scanned on every call; a `tickets/` folder
  is a board only if it has `unblockd.json` (opt-in). `TICKETS_DIR` / `UNBLOCKD_BOARDS` add
  explicit folders. First board = default. API: `/api/b/<board>/...`; un-prefixed paths = default.
  The UI keeps the board in `?board=` and localStorage. The board switcher is the page title: `#bpanel` (a `.spanel` `<details>` whose `<summary>` holds the h1 + chevron, in `MENUS`), list built by `loadBoards()` into `#bbody` from `BOARDS` (also what chat `@board` completion and `#board/ID` refs read; there is no `<select>` any more). One board: `#bsum` is `inert` (plain title, no chevron). `Shift+B` opens it, arrows/Enter pick, Esc closes. `b` stays free for a planned add-blocker shortcut (UI-8). **View switch**: Board | Graph | Docs | Map | Roadmap is `#viewSeg` (`.vico-g`, built by `paintViews(v)`) in `.trow` right after the board title, a separate control from `#bpanel` (clicking an icon never opens the board menu; it shows with one board too). 16px stroke SVGs (`VICON`); the active view shows icon + label, the others icon-only (owner decision 2026-10-24, UI-52: compact wins; the names live in the tooltips) with `title` `Graph (g)` / `Docs (d)` / `Map (m)` / `Roadmap (r)` + `aria-label`, `aria-pressed`; buttons keep `data-view` (what `ui_smoke.mjs` clicks). The right cluster is actions only (Ask Claude = the chat, New ticket, Agents, ⚙, ?). Header tooltips carry their key (`New ticket (n)`, `Graph (g)`...) and the `?` button (tooltip `Shortcuts (?)`) opens the `?` sheet: when adding a shortcut, update the sheet AND the tooltip. **Header** = ONE row: `.trow` holds logo, `#bpanel`, `#viewSeg`, `#needsBadge`; `.hdr` holds the actions; it wraps only at <=600px. There is no subtitle (`#sub`), no "Press ? for shortcuts" link and no status strip: counts live in the column heads and `renderAgBtn` (called by `render`) labels `#agBtn` `Agents · N live` (plain `Agents` at 0).
- **Routing**: a ticket's `agent` = explicit `agent:<name>` tag, else the first profile sharing a
  tag or its pillar. `list`/`next_ready` `agent=` takes a profile or a worker name (resolved with `profile_of`, same as claim). `work_plan` = ready tickets NOT owned by a human, grouped per profile with
  its instructions/model, for an orchestrator to fan out.
- **Claims**: `claim(agent)` takes the best claimable ticket for the worker's profile (profile =
  the one its name equals or starts with `<name>-`, e.g. backend-1 -> backend: `Store.profile_of`. On a board WITH profiles a name matching none is refused, listing the profiles; an explicit `profile=` is allowed; boards without profiles accept any name): ready, not human-owned, not
  claimed, `touches` not overlapping a live claim. Sets status doing. A file lock
  (`tickets/.unblockd/lock`, re-entrant within one Store) makes it atomic across processes; `create`, `update`, `delete` and `split` take it too (next-id + write, and read-modify-write, would otherwise race).
  `heartbeat` keeps it alive; no heartbeat for `lease_minutes` -> swept back to todo on the next
  read. `complete(id, agent, summary, files=None, refs=None, handoff=None)` needs a summary and adds it as a `complete` note (with `status` and the `done_when` it was finished against); it also stores `result` {summary, files (paths changed), refs (PR / commit / URL), handoff (<= 2000 chars: what dependents must know), by, at, principal (only when the claim had one), approved_by / approved_at (only `approve()` sets them; see Review gate)} (lists of <= 50 strings of <= 300 chars; bad input is refused before anything changes; MCP `complete`, CLI `complete --file/--ref/--handoff` (repeatable), REST body keys `files`/`refs`/`handoff`, `Remote.complete`). `knowledge.context()` adds `upstream` = for each id in the ticket's `blocked_by` that has a `result`: {id, title, summary, files, refs, handoff}. The drawer does not show `result` yet (UI-6). **Principal** (team use: the human an agent works for): `claim` / `claim_next` / `claim_ticket` take optional `principal` (MCP arg, CLI `--principal` defaulting to env `UNBLOCKD_PRINCIPAL` on claim/heartbeat/release/complete, REST body key, `Remote`); it must be a `kind: human` owner or the claim is refused listing them. Stored in `claims.json` (so in the derived `claim` and `agents_now`), copied by `complete` to `result.principal` (`RESULT_KEYS`; `reject` clears `result` as before) and carried on the `claim` / `complete` / `release` activity events (`_log(principal=)`). `Store._holder` (heartbeat / release / complete) also refuses when the claim AND the call name a principal and they differ, so two humans' workers with the same name cannot act on each other's claim; `_holder_only` (update / split / delete) and `ask` still compare the name only. With 2+ human owners and no principal the claim result has `warnings` (not stored); solo boards get nothing. It is a self-declared label until per-user tokens exist. UI: card tooltip and drawer claim line "backend-1 for Omri", `resultHtml` "Done by backend-1 for Omri". **Lease for LLM work**: `claim()` returns the ticket plus `lease_minutes`, `expires_at` (heartbeat_at + lease, UTC ISO) and `previous_attempts` (`Store.attempts(id, 5)`: `expired`/`release`/`rejected` events from the activity log as `{agent, outcome: expired|released|rejected, at, note}`, newest first; nothing stored). Every front door gets them because they all call `claim`. A `claim(tid)` refusal names the cause (`_unclaimable`: proposal, question, blocker ids, human owner, overlapping holder); `worker_profile(agent)` is the one place a name matching no profile is refused (claim and the MCP `next_ready(agent=)`). `Store._keepalive(tid, agent)` (caller holds the lock) renews the heartbeat when `agent` holds the live claim; `add_note(by)` and `update(agent=)` call it, so no new params. `WORK_LOOP` step 3 tells workers to read `previous_attempts` first. **Failing tickets**: `Store.failing(n=3)` = `{id: attempts}` for tickets with >= n failed attempts since the last human touch (an `answered` event, or a `note` whose author is not an agent; agent = `profile_of(name)` resolves OR that name has a `claim` event on that ticket, so boards without profiles work). `_needs()` lists an unclaimed one as `stuck` (precedence unchanged) with `failed` ("Failed 3 times (expired ×2, rejected ×1)") and `attempts`. **Caps and notes**: `complete` summary <= `SUMMARY_MAX` (10000) and handoff <= 2000, clear errors. Every note goes through `_append_note`: explicit writes (`add_note`, `ask`, `answer`, `reject`, `complete`) are refused when body + notes would pass `BODY_MAX`, before any claim or status changes; automatic ones (expiry sweep, `release` reason) are skipped silently (the activity log still records the event). `result` is set only by `complete` (refused in create/update, readable) and `reject` clears it so dependents' `upstream` never shows rejected work. `answer`/`reject` refuse an empty `by` (REST/CLI still default to `human`). **Review gate**: with `review: true` in the config, `complete()` sets status `review` (its note has `status: "review"`) instead of `done`. `review` is open work: it does NOT unblock dependents (decided on purpose: the human look is the point), is not claimable, and a human moves it to `done` (or back to todo) with `update` or, to record who looked, `approve(id, by)` (MCP `approve_ticket(id, by)`, CLI `approve ID [--by]`, REST `POST tickets/<id>/approve {by?}`, `Remote.approve`): refused unless status is `review`, for a worker-shaped `by` (`_human_only`) and for `by == result.by` (the completer); it sets status done, `done_at`, `result.approved_by` / `approved_at` (a `review` ticket with no `result`, moved there by hand, gets no invented result: only the note and the `approved` event name the approver), appends the note `Approved by X` and logs `approved` (with the claim's principal). A plain `update` to done leaves them empty on purpose (nobody approved), and any update that moves a ticket OUT of done strips them (that is the Undo of an approval). `reject` still pops the whole `result`. The UI shows a Review column (plum) before Done when the config has `review` or any ticket is in that status (`setCols()`; the `--cols` CSS var sizes the grid); a review ticket is not Free (`isFree`: it waits on a human, not on work) and the digest lists a `complete` whose ticket is still in review under "Ready for review", not Finished. `claim_next(agent, profile, note)` = `claim` that never returns a bare None: when empty it answers `{ticket: None, reason, counts}` (`reason` conflict = ready tickets whose touches overlap a live claim: retry; waiting = open work but none ready (in flight / review / waiting on a human / blocked); dry = nothing open for the profile; `counts` = in_flight, ready_conflicting, in_review, waiting_on_human, blocked; `ids` = the same keys with ticket ids; `orphaned` = `doing` tickets with no live claim, also inside in_flight: reported only, never claimable, because claims.json is not in git and a person may have moved it by hand). MCP `claim_next`, CLI `claim` (without `--id`) and `POST /claim` use it (`Remote.claim_next`); `WORK_LOOP` tells workers to retry on conflict and stop on waiting/dry, reporting the `ids` (and naming `orphaned` ones to the human). The MCP `next_ready(agent=)` wrapper (not `Store.next_ready`, which web/CLI/chat use for humans) drops human-owned tickets and refuses a name matching no profile; server `instructions` point workers at `claim_next` / `work_loop`. `knowledge.with_context` passes an answer without `id` through. `ask(id, agent, question)` (MCP `ask_human`, CLI `ask --question`) is for a decision only a human can make: it ends the claim, sets `waiting_on` = question (status stays todo) and logs `question` (limit `QUESTION_MAX` = 1000 chars, the error says so; the `waiting_on` field and the edit form's input have the same cap, so saving a ticket with a long question works); a todo with a non-empty `waiting_on` has `effective_status` pending, so it is neither ready nor claimable until a human clears `waiting_on`. The question is also kept as a `question` note, so it survives the clearing.
  **Answer / reject** (the human side): `answer(id, by, text)` is refused unless `waiting_on` is set; it adds an `answer` note (`q` = the question, `text` = the answer), clears `waiting_on` (ticket is ready again) and logs `answered`. `reject(id, by, reason)` is refused unless status is `review` (reason required); it sets status todo, adds a `rejected` note (text = the reason) and logs `rejected`. Front doors: MCP `answer` / `reject` (`id, by, text|reason`), CLI `answer ID TEXT [--by]` / `reject ID REASON [--by]` (by defaults `human`), REST `POST tickets/<id>/answer {by?, text}` / `POST tickets/<id>/reject {by?, reason}`, `Remote.answer` / `Remote.reject`. `notify.py` reports both (`💬` answered, `↩` rejected), and `WORK_LOOP` step 3 tells a re-claimed ticket's worker to read the latest `notes` first.
  **Notes** (`add_note(id, by, text)`; MCP `add_note(id, agent, text)`, CLI `note ID TEXT [--by]` (default `human`), REST `POST tickets/<id>/notes {by?, text}` (`by` defaults to `human`), `Remote.add_note`): under the lock, appends `{by, at, kind: "note", text}` to the ticket's `notes` list (module helper `_append_note`, the one writer of notes) and logs `note`. **Notes are a field, not body text** (they used to be `\n\n— <by>, <ISO>: <text>` lines appended to `body`, which merged badly in git and had to be re-parsed): `notes` = `[{by, at, kind, text, q? (answer), status? + done_when? (complete)}]`, kinds `NOTE_KINDS` (note, question, answer, approved, rejected, accepted, released, expired, complete), read-only for create/update ("add one with add_note"), so `body` is only the description and the edit form (which saves `body`) can no longer clobber a note. ## Why files, not a database

Decision, don't re-litigate: **one JSON file per ticket in the project's git repo is the product.** Tickets are reviewed in PRs next to the code
they describe, work offline, diff and merge like source, and agents need no server to read or write them (CLI/MCP open the folder).
A database would give up exactly that. Measured at 5,000 tickets (Windows, 2026-10-20, synthetic board): before the cache `list()` 0.41 s, `get()` 0.40 s, claim + release 1.6 s (0.7 s holding the lock, 15,000 file reads); with it `list()` 33 ms, `get()` 14 ms, claim + release 0.24 s, `/api/needs` 63 ms.

**The cache** (store.py `_RAW` / `_DEC` / `_LOG`, module-level so every Store on a folder shares them, which matters because the web server builds one Store per request): `_scan()` = one `os.scandir` per call, a file is re-parsed only when its `(inode, mtime_ns, size)` stamp changed (`os.replace` makes a new inode, so a rewrite within one clock tick is still seen; DirEntry on Windows has no inode, but its mtime is 100 ns); `_board()` = the decorated board by id, re-derived only when the stamps, `claims.json`'s stamp, the attachment names, the date or the config changed; `_events()` = the activity log parsed incrementally (only the bytes appended since; another inode or a shorter file = reread; a half-written line waits). Files stay the only truth: nothing is written back, and a git pull, a hand edit or another process's write is seen on the next call. `list()` / `get()` / `_all_raw()` return copies (`_copy`, two levels deep): never hand out a cached dict. `unblocks` is one bitset pass over the reverse `blocked_by` graph, not a DFS per ticket.

The real limits, and what already answers each:

| Limit | Answer |
|---|---|
| The file lock only works on one filesystem, so every agent had to run where the tickets are | Remote CLI: `UNBLOCKD_URL` sends commands to the one web server, whose Store does the locking |
| Every open browser re-downloaded the whole board every 4 s | `ETag` + 304 on GET; the UI sends `If-None-Match` |
| `activity.jsonl` grew forever and was parsed whole | Rotated at 5 MB, read newest-first and stopped early |
| Parallel `create`/`update` raced (lost tickets, lost claims) | `create`/`update`/`delete`/`split` run under the same lock as claims |

Revisit SQLite only for the **runtime** state (claims, activity), never for tickets, and only if remote mode stops being enough.

## Traps that already bit

- `.board` is the board's grid class: any other element with class `board` turns into a 4-column
  grid. (Board links in chat use `.bref`.)
- `[hidden]{display:none!important}` is required: component classes set `display` and would
  override the attribute.
- `_locked` steals a lock older than 30 s through `_steal`, which holds `lock.steal` and re-checks the age first. A bare `lock.unlink()` after reading the stale mtime lets two processes both "steal": the second deletes the fresh lock the first just created and both run the critical section. `claims.json` that is not valid JSON raises `TicketError` telling the user to delete that file (claims are runtime state, live workers re-claim); it used to read as `{}`, silently dropping every live claim. After `_steal` the loop falls through to the deadline check and sleep (a stuck `lock.steal` guard must not busy-spin or outlive the 10 s deadline).
- **Windows lock re-create**: right after the holder deletes `lock`, Windows keeps it "delete pending" and `os.open(O_CREAT|O_EXCL)` raises `PermissionError`, not `FileExistsError`; `_locked` once let that escape, so under contention a concurrent `add_note` was lost (flaky test_claims concurrent-note test, ~1 full run in 4). It now waits and retries like for a held lock (a real permission problem still fails after the 10 s deadline, with a clear message).
- **Indicator measured before its frame** (UI-37): `slidePill` must add `.sl` (which makes the control `position:relative`) BEFORE it creates and measures a new `.ind`; measured first, `offsetLeft/Top` were relative to the drawer (e.g. 20, 124 px) and a ticket's status pill slid in from below on its first open.
- **Holder rule** (`Store._holder_only`): when a ticket has a live claim and the caller names itself as an agent that is not the holder, `update` (any field), `split` (`by`) and `delete` (`agent`) are refused; no agent identity (web without `agent`, human CLI) is unchanged. MCP `split_ticket`/`delete_ticket` require `agent`; CLI `--agent` on update/delete (`split --by`); REST `DELETE tickets/<id>?agent=`, `Remote.delete`.
  **Worker guardrails** (accident prevention, NOT security: an agent with a shell can edit the JSON files; per-user tokens are the later fix). "Worker-shaped" = the name resolves to a configured profile (`profile_of`: `backend`, `backend-1`). Such an actor cannot `answer` / `reject` / `accept` / `approve` (`_human_only`: "tell the human (ask_human) or add_note"), cannot `update` status to doing / done / review ("use claim_ticket / complete / ask_human"; todo is allowed; closes the review-gate bypass and ghost `doing`) and cannot `delete` a human-owned ticket. For EVERY actor: no self-approval (`answer` by == `asked_by`, `accept` by == `proposed_by`, `approve` and `reject` by == `result.by`). Boards without profiles, and names matching no profile (`claude`, `omri`, `human`, the owner's own Claude on a solo board), are unrestricted, so the solo flow is unchanged. Tests: tests/test_guardrails.py.
- Anything `chips()`/`slidePill` reaches runs during init (`applyConfig` -> `renderBar`), so every `const` it reads must be declared above the first call: `reduce` used to sit at line ~1215 and the page died with "Cannot access 'reduce' before initialization". A `startViewTransition` callback is async: tests (and code) that click a view button must wait for the state (`waitForFunction`), not assert right after the click.
- **Git worktrees** (`Store.rt`, `store.linked_worktree`): each worktree has its own copy of a committed `tickets/`, so a CLI run there used to get its own lock and its own (gitignored, empty) `claims.json` and could claim a ticket another worktree's worker held; where `tickets/` is NOT committed (this repo: the board is a separate repo) the worktree had none and `Store()` silently created an empty board. Now a tickets folder inside a linked worktree (its `.git` is a file whose gitdir has a `commondir`; submodules have none) keeps runtime state in the main checkout's same folder, and the CLI refuses a missing `--dir`. Every runtime path goes through `store.rt` (github.py `load(rt)`, notify.py), never `tdir / ".unblockd"`.
- `pending` is derived, never settable: the bulk bar, move menu and drawer omit it, and the chat prompt lists it only as a filter value.
- `pkill -f <pattern>` in a shell whose own command line contains the pattern kills the shell
  (exit 144). Use `pgrep -f "[u]nblockd.web" | xargs -r kill` in a command that doesn't start a
  server too.
- Expired claims are swept at the START of `list()`/`get()`; sweeping inside `_decorate` was too
  late (tickets were already read as doing).
- `_locked` must stay re-entrant: `claim()` holds the lock and calls `next_ready()`, which may
  sweep expired claims under the same lock.
- urllib capitalises header names (`X-api-key`); compare headers case-insensitively in tests.
- A regex like `/^BUG-10$/` never matches `id + ' ' + title` (the `$` meets the title), hence the extra test on the bare id in `matches()`.
- Closing the drawer rewrites the URL: keep `location.search` (`?board=`) when clearing the hash.
- `compose.yaml` must pass `.env` values into the container explicitly (`environment:`); `.env`
  alone only feeds `${...}` interpolation.
- An ETag (or any "last seen" token) must be stored WITH the data it describes. `loadNeeds` once set `nEtag` before parsing the body; when a newer request superseded it, the data was dropped but the tag stayed, every later poll got 304, and the panel never showed the answer (flaky smoke: ~1 run in 3). Race-test anything with overlapping fetches by firing two refreshes at once.
- The Needs panel and the drawer share `#scrim`: whoever closes second must not leave it up or hide it from the other (`closeNeeds(true)` = the drawer is taking over; `openNeeds` closes the drawer first, then shows the scrim). `Esc` order in the keydown handler: hint (`p`), command palette, `?` sheet, menus, panel, drawer.
- `<input value>` drops newlines: a multi-line draft collapsed back to the one-line input shows them stripped, so `submitNeeds` sends `DRAFTS[key]`, not the field's value.
- `[hidden]` on `#depSeg` works only because of the global `[hidden]{display:none!important}`: `.vico-g` sets `display:inline-flex`.

- **"Waiting on <first word>" bug**: a question's `waiting_on` is free text (the question), never a person. Cards and drawer show `Question from <asked_by>` for an agent question and `Parked: <waiting_on>` for a hand-set one; never split `waiting_on`.
